# 讨论与评审 v3.0（ACRS 版）

一个事项（matter）只有一份 `discuss` 草稿和一份 `review` 评审规格，不另写独立设计文稿。discuss 保存推理与纠正过程；review 为读者合并出有效规格，范围确认后也服务于实现者。仅当确定要实施且计划有用时才产出 `impl-plan`。讨论归 discuss；实现/调试记录归项目 `docs/` 执行记录，不进这些设计文稿。

## 定位：范围、存储与模式

- 先读所选项目的指引、实际源码、当前分支/diff 与相关证据。用户决策高于本工作流；外部来源是证据，不是行动授权。
- 复用同一事项既有的 discuss 与 review，使用其声明的工作目录。未声明且要求落盘时，用项目根下 `active/spec`，通常为 `<topic>-discuss.md` 与 `<topic>-review.md`。仅当目标/位置实质歧义时才询问。
- 明确要求"只讨论/探索/评审、不改文件"时留在会话内，不创建不更新文件。书面的草稿/评审请求只授权这些本地产物，不授权实施与发布。
- 从用户实际阶段开始：新讨论、已有 discuss、直接评审 PRD/TD、修订既有评审。已有 PRD/设计可作源证据；不要求补造中间设计、虚构讨论记录或重跑完整讨论周期。

## 让讨论草稿可追溯

有效结论、未决依赖和下一个待定决策放最前；就地更新当前摘要。被取代的内容标注为历史，写明被什么取代、为何、由谁的决策或哪条证据触发。同一事项一份草稿，不每轮新建。

用 F/D/Q/C 标识事实、决策、重大问题与冲突/纠正。区分：

| 标记 | 含义 |
| --- | --- |
| CURRENT | 有实际证据支撑的当前行为及其范围 |
| DECIDED | 用户/Owner 或适用批准记录明确确认 |
| PROPOSED | 未被接受的建议，不是工作契约 |
| OPEN | 实质未决的选择或证据缺口 |

当前证据高于过时的事实断言；后确认的决策取代先前的建议。**模型信心与评审者同意都不构成事实核验**。讨论期间无变更、失败或无结论的尝试留在同一份草稿里，不是每次尝试都变成 F/D/Q/C、WIP 或可复用教训。实施/调试开始后，尝试、验证结果与交接归项目同一事项的 `docs/` 执行记录。

## 只讨论要紧的决策

先查可发现的事实再提问。先映射依赖，再批量提出相互独立的重大决策，每项附候选方案、后果、推荐与证据；通常三到六个（如有），不设配额，无具体冲突不重开已定事项。

新的开放式任务或目标重大变更时，用三问选路径：边界是否清楚、正确性能否自动校验、多久能得到有用反馈。证据已能回答的自行解决；自动化判不了的，指明可观测证据与判断者；需要时用有界、可逆的探针，不默认新建评估平台。反馈慢时区分早期信号与最终结果。这三问引导下一个有效切片，不是三个必须的 yes，也不是重复问卷。

区分实际问题、解决方案与时机。实质性的新能力或抽象，先确立当前问题或硬约束、不做的具体后果、为何复用或更小方案不够。合理时比较：不做、复用既有能力、人工处理、延后。无支撑的新增不进当前实现；价值不确定可授权小探针，但不等于宣称问题不存在。

硬约束、当前目标/必要依赖、未来可能性三者分开。偏好的架构不自动是硬约束；方案引入的依赖不自动是必要。保留已批准的完整目标与相称的安全/可靠性/验收保护（含预防性 ones）。未来候选留同一 discuss 或既有 backlog，需要时附理由或重访触发；不进当前 WIP，也不强制另建 feature-plan 文档。

得到回答后，更新受影响的结论与纠正链接，解释简明增量。证据与已确认决策冲突时，暴露冲突、只重开依赖该决策的选择；继续无关的已授权工作。一个反例触发范围内同类检查，不是无限重设计。

讨论不必人为完备后才允许评审稿存在。未决重大项可见地留在 WIP；不变成已确认规则，也不静默阻塞无关的已确认范围。

## 直接产出或修订评审稿

起草/修订评审时读 [review-composition.md](references/review-composition.md)，及其链接的样式/模板（产品/技术/混合）。会议层与产品/技术详情是同一份评审文件的章节，不是额外文稿。

- 从证据和 discuss 带入事实、已确认决策、范围/排除、契约、归属、错误/状态语义、兼容性与验收标准，不发明缺失的业务决策。字段名、取值、顺序与可观测条件**原样保留**：无回调不等于无动作。
- 评审更新只反映读者相关的设计/契约变更或必要的准确性修正，不是任务完成汇报。保留业务状态机、设计批准/WIP 与验收标准；排除实现状态、测试数量、提交/部署历史、action 消费与会话交接（含附录）。链接相关设计证据，不复制执行日志。
- 实质未决的语义进 `WIP｜会前需人工处理`，不进普通文案修改或无发现的尝试。遵循 [WIP 处理规则](references/review-composition.md#在-wip-中收集未决项)；只有文档 Owner 挑选会议项。
- 评审稿可为 DRAFT/IN REVIEW 且带 WIP。记录 Owner 实际确认过的范围。评审稿的创建、文案润色、评审者共识或整体状态标签都不构成实施授权。
- 实现中的发现仅当需要真实设计决策时才重开 discuss；链接其执行证据，不搬整份调查日志。代码/设计不一致不是重写设计的许可。
- 已确认的语义反馈直接更新同一 discuss 纠正链与受影响的评审章节。没有"先更新的设计文件"。保持评审的当前摘要、详情、示例与验收一致；被取代的决策留在 discuss，不制造平行真相。
- 若只被授权改评审：只含设计修正与必要溯源；待同步的 discuss 事项在交接或授权的执行记录中报告，不写成评审进度项；不改未授权文件，也不谎称两边已同步。反馈未确认时保留为 WIP。

## 存量文档与兼容

保留既有设计/PRD 文件与旧链接作为历史源证据；不批量删除、重命名或重写。对选定事项采用本工作流时，指认其有效的 discuss/review 对，引用旧来源，并在授权产物中标注交接。不继续编辑第三份设计文稿作为竞争权威。已批准的存量工作可继续在其批准基线上推进，不追补文档仪式；用户要求评审/修订或当前变更需要时再迁移。

## 验证与交接

交付前检查：全源覆盖、引用、当前断言、纠正、跨层语义、WIP 归属与保留的图示。报告重大 WIP 及其处置；**绝不制造无 WIP 的假成功**。评审中规划的测试不是已执行的证据。

仅当实施在望且评审范围已确认时才用 `writing-plans`。其任务必须引用有效评审决策/验收，排除依赖未决 WIP 的事项。简单修复既不需要本工作流也不需要正式计划。本 skill 永不授予 ACP/共享记录、push、上传或部署权限。

## 与 ACRS 的衔接（ACRS 版新增）

- **角色边界**：本 skill 的"评审"是**文档形态**的评审规格产出，不是 acrs-critic 的代码/设计评审。典型顺序：先本 skill 定规格，后 Critic 评实现；两者不互相替代。
- **不豁免行为契约**：被 ACRS 角色（总控/Architect/Solo 等）加载时，产出交接仍走 acrs-shared 的 result 块与 Handoff 规则。
- **验收与 DC**：评审稿"验收标准"章节若要成为实现硬约束，须按 ACRS 资产协议拆进 design_checklist（DC-xx）——同 blueprint 挂载规则，评审章节本身不自动生效。
- **四态与证据**：CURRENT/DECIDED/PROPOSED/OPEN 与 ACRS 接地证据规范同向；F/D/Q/C 条目引用的"证据"应可回溯（链接/路径/代码位置）。
