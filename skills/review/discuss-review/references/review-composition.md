# 评审稿组装（review composition）

评审稿是唯一的合并规格。讨论草稿保存证据、已确认决策与纠正；没有中间设计文档。只有明确确认的评审范围才有资格进入实施计划。

## 在 WIP 中收集未决项

首次起草时，`WIP｜会前需人工处理` 是所有实质未决项的唯一收集点，包括冲突、缺失事实、未核验的当前行为、语义歧义与潜在会议决策。

Agent 组织证据并给出推荐；**不得代替文档 Owner 决定某项属于结论还是会议议程**。不因 Agent 发现了一个问题就单独创建 `待决策点`。

人工处理后，文档 Owner 为每个 WIP 项选择一种处置：

1. 直接确认，把结论移入相应的会议层或详情页章节；
2. 移入 `待决策点`（须开会决策），可保留或修订推荐；
3. 保留在 WIP，直到所需材料或核验存在。

`WIP` 不是隐藏 TODO，也不是决策表。不要在评审文档中另设风险或下一步行动类别。

## 选择模板

起草前先读 [two-layer-style.md](two-layer-style.md)。

- 技术决策：从 [technical-review-template.md](../assets/technical-review-template.md) 起步。
- 产品需求：从 [product-requirements-review-template.md](../assets/product-requirements-review-template.md) 起步。
- 产品+技术混合评审：用一个共享会议层，产品/技术详情页分开；标注每条结论由哪个角色确认。

## 写会议决策层

前层要让产品经理、交付负责人与非技术领导**不打开详情页也能跟上**。用平实的业务语言；仅当代码标识符本身就是决策对象时才写它。

按以下顺序组织模块：

1. **建议结论**：一句话 + 简短决策表。
2. **目标与范围**：为什么现在要解决这个问题、目标结果、硬约束、最小充分方案与关键取舍、明确排除项、重要假设。概述如何/何时有用证据能判断该方案；区分早期信号与最终验收。用既有章节，不加审计表。未来可能性不进当前范围/WIP（除非影响当前重大选择）。
3. **主流程**：从触发到可见结果的一条路径。源材料已有能解释该路径的原型或截图时，把相关资产放这里并说明各自覆盖什么。不发明图示，也不把可用的源图示藏进详情页。
4. **归属与边界（按需）**：仅在真实的用户/团队/系统/数据/外部契约边界时使用。不把 Controller/Service/UI 分层当作会议级归属。
5. **待决策点**：只含文档 Owner 从 WIP 明确移入会议讨论的事项。每项写明推荐与需要谁确认。没有被移入的就简要说明，不发明条目。
6. **`WIP｜会前需人工处理`**：紧跟 `待决策点` 之后放引用块，收录仍需人工准备或核验的重大项。

不要在这一层放全量 schema、API 字段、代码、完整规则集或每个异常分支。只读前层的读者必须仍能做出范围、归属与优先级的决策。

## 写 WIP 块

用简短引用块，不用普通决策表。每项包含：

```md
> **WIP｜会前需人工处理**
>
> - **[矛盾 / 缺口 / 未核验 / 语义不清]** <问题>
>   - 证据：<来源章节、代码或互相冲突的表述>
>   - 需要人工处理：<需要确认、统一或回写的内容>
>   - 推荐：<建议直接确认写入正文，或建议移入待决策点；说明原因>
>   - 由文档 Owner 决定：<直接回写正文 / 移入待决策点 / 保留 WIP>
```

只保留影响范围、行为、契约、验收或评审能否有效进行的重大项。普通文案修改不用 `WIP`。

## 写详情页

详情页是**查证面**，不是第二份会议叙事或执行日志。保留设计相关的事实/溯源、业务状态、发布策略与验收标准；把实现进度、测试结果、部署历史与交接留在链接的执行记录里。设计 WIP 不是实现 backlog。为正确性、术语稳定与检索优化：

- **技术详情页**：背景、当前事实与证据；模型与字段；状态机；调用/事件契约；并发、事务、幂等、重试、补偿；兼容性；发布；测试与验收。
- **产品详情页**：背景、用户问题与证据；场景；完整功能细节；业务规则与边界情况；原型与交互细节；依赖与数据定义；非功能需求；发布与验收。

映射、规则、职责、决策用表格。顺序问题用时序图，状态迁移用状态图，事实性理由用简洁行文。不在旁边逐行复述表格或图的每个箭头。详情页不必像演示文稿，但**不得自相矛盾，也不得与会议层矛盾**。

## 验证与汇报

宣称文档就绪前：

1. 扫描全源、会议层与详情页：缺证据、未核验断言、矛盾定义、编辑引入的语义变化。针对当前目标、约束与更小替代方案质疑无支撑的能力或抽象；反对意见必须指明具体的新增与证据，不能只贴"过度设计"标签。不缩减已批准目标或必要保护。
2. 确认每个 `待决策点` 都由文档 Owner 明确选中，且带推荐与确认角色。
3. 确认其余实质未决项都留在 `WIP`，没有被静默猜测或自动升级为会议决策。
4. 确认既有图示资产被正确放置，或有理由地明确排除。
5. 确认会议层不读详情页也能理解；详情页可检索且一致。

最终交付消息中，分别报告 WIP 数量与未决会议决策数量，并简要指认条目。仅在未被指示之处请文档 Owner 处置剩余 WIP。把 WIP 移入 `待决策点` 只改变位置，不改变未决状态。零 WIP 只说明 WIP 中没有遗留项，**不证明所有实质缺口或矛盾已解决**。只有源与两层评审都支持该结论、且 WIP 与会议决策均无遗留时，才可宣称无重大遗留。
