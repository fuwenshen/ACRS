## F-001（B-1）register source 校验遗漏 → Core Candidate【本 case 核心】

- **现象**：Backend 首次交付 register 缺 source 校验——四字段有 FinAssert 而 source 无，空白值可落
  00000 脏数据且 verify 阶段 10001 判死，形成"登记即永久不可自愈"。Critic 独立评审拦截（BLOCKER），
  修复后复审翻绿。
- **分类**：Core Candidate——系统边界输入验证破坏 + 对外契约违反，任何平台/团队都会犯，行为不绑平台。
  证据链完整（代码证据 + 集成测试复现 + 不可自愈闭环推演），质量达 RI 级。
- **处置**：**不修 Core、不修 RFC**（本工程已修复）。登记 RFC-000B §5 Pending（独立暴露 1 次，未达
  ≥2 门槛，按单次深度证据登记，待 Admission Review 独立判定 Admitted/Deferred/Rejected）。
- **终态**：Pending（首条来自真实闭环的 Core Candidate，也是 RFC-000B 首次被真实使用的试金石）。

## F-002 门禁执行序假象（spotbugs 从未执行却被当基线 0）

- **现象**：pmd-check 先挂导致 spotbugs 从未执行，中间基线"spotbugs 0"实为未覆盖假象；终跑
  mvn clean verify 退出码 0 时三门禁才真实全执行。已修正并终验。
- **分类**：Convention。诊断 **A·兑现失败**——R12"无退出码的完成 = 违约"已覆盖此语义（报通过
  但无真实执行记录 = 违约实例），无需新增规则。
- **处置**：无体系改动；执行侧教训 = 多门禁链式执行时，中间态"某门禁 0"须核对真实执行记录才算数。
- **终态**：**A·Closed**（R12 承载，DC 全勾对后终验覆盖三门禁）。

## F-003 质量豁免配置与 POM 注释不符（kernel 包未实际豁免）

- **现象**：豁免声明与实际配置不一致，注释说豁免了、配置没生效。
- **分类**：Convention（工程规范约定：注释/文档与配置必须一致）。诊断 A——"注释即契约"属既有工程
  纪律范畴，项目侧修复即可，体系不为此立规则（P8：不预设）。
- **终态**：**A·Closed**（项目侧已修正）。
